# Privacy

**English · [简体中文](PRIVACY.zh-Hans.md)**

SixOne keeps a history of your clipboard on your Mac. That history is among the most sensitive data on a personal computer — it routinely contains passwords, one-time codes, private messages, and the filenames of documents you are working on. This document states exactly what the app does with it. It describes the code in this repository, not a promise about future versions.

## 1. What is recorded

SixOne polls `NSPasteboard` every 0.5 s and records an item when the pasteboard changes, subject to the two filters below. Five kinds of content are recognised: **text, image, file (including multi-file groups), link, colour**.

Both filters run **before any clipboard bytes are read**, so refused content never enters the process's memory:

1. **Do-not-record markers.** If any pasteboard item declares one of these types, the whole copy is discarded:

   | Type | Set by |
   | --- | --- |
   | `org.nspasteboard.ConcealedType` | Password managers and apps that handle secrets |
   | `org.nspasteboard.TransientType` | Apps marking content as not worth keeping |
   | `org.nspasteboard.AutoGeneratedType` | Machine-generated content |
   | `com.agilebits.onepassword` | 1Password |
   | `de.petermaurer.TransientPasteboardType` | Various |
   | `com.typeit4me.clipping` | TypeIt4Me |
   | `Pasteboard generator type` | Various |
   | `com.apple.is-remote-clipboard` | Universal Clipboard from another device |

   The list lives in one place: `PasteboardSnapshot.doNotRecordTypes`.

2. **Source-app ignore list.** Copies made while an app on your list is frontmost are neither read nor recorded. Manage it in **Settings → Privacy**; it ships with **Passwords** and **Keychain Access** pre-ignored, and you can add any app.

   Note the limitation: the source is whichever app was frontmost when the pasteboard changed, which is not always the app that wrote the content — a browser extension copying on behalf of a password manager is the standard case. That is exactly why filter 1 exists, and why it matters more.

Once a copy passes both filters, parsing happens off the main thread: converting HTML to rich text, pinning security-scoped bookmarks for files, and generating a thumbnail never block the panel.

**Nothing is recorded retroactively.** On launch the app takes the current `changeCount` as its baseline, so whatever is already on the clipboard is not picked up: clearing history and restarting does not re-import the leftover contents.

## 2. Where it is stored

| | |
| --- | --- |
| **Signed (sandboxed) build** | `~/Library/Containers/dev.sixone.SixOne/Data/Library/Application Support/SixOne/SixOne.store` |
| **`CODE_SIGNING_ALLOWED=NO` build** | `~/Library/Application Support/SixOne/SixOne.store` |

The store is deliberately namespaced (`SixOne/SixOne.store`) rather than using SwiftData's default location — the shared `~/Library/Application Support/default.store`, where any SwiftData app lands on the same file. It is a plain SQLite database, and the project is unreleased with **no migration path**: a schema change may require clearing history.

**There is no encryption beyond the container's own permissions and FileVault.** If you need history to be unreadable at rest, rely on FileVault — and note that image and rich-text bodies are also written to Core Data external-storage files beside the store.

In-memory caches (row thumbnails, file-group icons, query caches) never touch the disk.

## 3. Network access

**The app makes no network requests of its own.** There is no `URLSession`, no socket code, no telemetry, no analytics, no crash reporting, no accounts, no cloud sync, no auto-update, and no third-party SDKs. The only URL in the code is the link to this repository on the About pane, which does nothing unless you click it.

One component *can* reach the network, so the line is worth stating precisely:

- **HTML preview** renders a `.html` file in an in-process `WKWebView`. A clipboard item can be a saved web page — a downloaded newsletter, say — so this is the one place where outside content meets a process that also holds the Accessibility permission. Three rules apply:
  1. **Content JavaScript is disabled.** Nothing in the page executes.
  2. **Only the initial local file load is allowed to navigate.** A clicked link is handed to your browser instead, and non-`file:` redirects (the `<meta http-equiv="refresh">` kind, which needs no script) are cancelled.
  3. **Remote content-transfer channels are blocked** by a `WKContentRuleList`: page navigation (`document`), scripts, `XHR`/`fetch`/`WebSocket` (`raw`), and popups.

  Remote *rendering* resources — images, stylesheets, fonts, media — are deliberately **allowed**. Blocking all `http`/`https` traffic looks stricter, but it turns every saved web page into a page of broken images, and with scripts off and the transfer channels shut there is no route by which your clipboard or your files can leave. If that rule list fails to compile, the app logs an error rather than previewing with a fence it believes is in place.
- **The residual cost, stated plainly:** because remote images load, a page you preview can still make your Mac fetch a URL. Whoever controls that URL learns your IP address and that the page was opened — the classic tracking pixel. They cannot learn anything from this machine. If you would rather not reveal even that, do not preview `.html` items.
- **Nothing from the page survives the preview.** The web view uses a non-persistent data store, so cookies, cache, and local storage stay in memory and are discarded when the preview closes.

The app's whole entitlement list is five entries, and each exists for a stated reason:

| Entitlement | Why |
| --- | --- |
| `com.apple.security.app-sandbox` | Standard sandbox; keeps the store inside the container |
| `com.apple.security.network.client` | WebKit requires it even to load a local file (Apple Feedback FB6993802), and the allowances above use it |
| `com.apple.security.exception.mach-lookup.global-name` (`com.apple.audioanalyticsd`) | WebKit's GPU process asks for that service on its media-decode path — the app is not collecting audio analytics |
| `com.apple.security.files.user-selected.read-only` | Only to let you pick an app in the Privacy pane's file panel |
| `com.apple.security.files.bookmarks.app-scope` | Lets this app resolve the read-only security-scoped bookmarks after a relaunch |

**How files are reached without folder entitlements.** SixOne deliberately requests no blanket access to Downloads, Movies, Music, or Pictures. A file you copy arrives with a sandbox extension granted by whichever app put it on the pasteboard, and that is what lets SixOne read exactly the files you copied — to de-duplicate them, thumbnail them, and preview them. Each path is then pinned as a **read-only security-scoped bookmark** (at most 100 files per copy, since creating one is synchronous I/O) so that access survives a restart or a move; when a bookmark can no longer be resolved, the app falls back to the original path, and a file it can no longer reach simply shows as unavailable rather than being guessed at.

## 4. Accessibility permission

SixOne asks for Accessibility (System Settings → Privacy & Security → Accessibility) for exactly one purpose: **synthesizing a single `⌘V` into the app you were using before the panel opened**, which is all that "paste into the previous app" means.

The app does **not** use `AXUIElement` to read other apps' interfaces, does not use Apple Events or AppleScript, and does not observe your keystrokes. The permission is used for status checks, one short-lived event tap that is created and destroyed immediately, and that one synthesized keystroke.

Without the permission everything else still works: you can copy items back to the clipboard and paste manually.

## 5. Retention and deletion

**Retention.** Settings → Storage offers 1 month / 3 months / 6 months / 1 year / unlimited (default: 3 months). Expired items are trimmed when a new item is captured, when a repeat copy de-duplicates into an existing one, at launch, when you change the setting, on an hourly sweep, and when the Mac wakes. The sweep exists because a Mac that stays awake and stops copying new content would otherwise never trim.

**Clearing.** Settings → Storage → Clear History, or the panel's *More Actions → Clear History*. Both ask for confirmation.

**What clearing does *not* do — please read this part.** SixOne deletes rows through SwiftData and saves. It does not `VACUUM` the database, and it does not erase SQLite's free pages or the write-ahead log. Deleted content can therefore remain recoverable inside the store file (and in Core Data's external-storage files for images and rich text) until those pages are reused. If you need data gone for good, delete the store while the app is not running:

```bash
rm -rf ~/Library/Application\ Support/SixOne          # unsigned build
rm -rf ~/Library/Containers/dev.sixone.SixOne         # signed / sandboxed build
```

Two more things outlive a "clear":

- **Corrupt-store backups.** If the store cannot be opened it is renamed to `SixOne.store.corrupt-<timestamp>` (together with its `-wal` and `-shm` sidecars) rather than deleted, so you can rescue it by hand. These accumulate; nothing prunes them.
- **Export temp files.** "Open / Share" writes a bitmap to `$TMPDIR/sixone-export/<uuid>/…` for the receiving app. Each one is a complete copy of that clipboard item, so they are pruned at launch once older than 24 hours, on a best-effort basis; a directory whose timestamp cannot be read is left alone rather than risk deleting a file another app is still reading. macOS's Quick Look may additionally cache thumbnails of previewed files in the shared user cache.

## 6. Logging

SixOne logs through `os.Logger` (subsystem `dev.sixone.SixOne`), visible in Console.app. Message interpolations are left at the default privacy level, so clipboard text and file paths appear as `<private>`; only a few deliberately-public values (error descriptions, counts and IDs, the configured hotkey, and a store file's base name) are readable. The app never writes to `stdout` and never `print`s clipboard content.

## 7. Reporting a privacy or security problem

If any of the above does not match the code, that is a bug worth reporting — and please do **not** open a public issue for it.

Use GitHub's private reporting: the repository's **Security** tab → **Report a vulnerability** (GitHub Security Advisories). If that is unavailable, contact the maintainer [@imhansai](https://github.com/imhansai) on GitHub and ask for a private channel first.

Please include the version or commit, your macOS version and chip, whether the app was built from source or run from Xcode, and whether the issue involves the Accessibility permission or the HTML preview. Expect an acknowledgement within about 72 hours — this is a spare-time project.

The areas most worth attacking, roughly in order: a way to make SixOne **record content it should have refused** (a bypass of the markers in §1); a way around the HTML preview's fence (§3); a way to make the paste path deliver `⌘V` to the wrong target or without user intent; and anything that leaks clipboard content into the system log.
